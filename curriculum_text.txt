     Study Principles
      • Build something every week — passive reading does not wire your brain. Code does.
      • Struggle is the signal. If it feels easy, you are not at the edge of your growth.
      • Solve 1 DSA problem every single day from Week 1. No exceptions. It compounds.
      • Finish one resource completely before starting another. Tutorial hopping is procrastination.
      • Teach what you learn — write blog posts, explain concepts out loud. It forces real understanding.
      • At 5 focused hours/day, this curriculum takes about 570 days (~19 months). You have roughly that much
        college left.
      • Consistency beats intensity: 2 focused hours daily beats 14 hours on Sunday every single time.
      • The interview habit at each phase is not optional — it prevents starting cold at Phase 5.


              When Stuck

              When stuck for more than 30 minutes: (1) Re-read the error message — it almost always tells you the
              answer. (2) Rubber-duck debug: explain your code out loud to yourself or a pillow — this works. (3) Search
              the EXACT error message in quotes on Google. (4) Post on Stack Overflow or a Discord — write a minimal
              reproducible example first. (5) Walk away for 20 minutes. Your brain keeps working.



              PH Context

              some Udemy courses on sale (~P300), DDIA and Hands-On ML books (~P1,500 combined). Everything
              else is free. Total investment: your time. There is no excuse.

     You said you have good logic. This is where it proves itself. Math is not memorization — it is precise

        • Basic probability, conditional probability
        • Bayes' theorem — essential for ML
        • Expected value and variance

     Part 3: Linear Algebra (Critical for ML)
        • Vectors: dot product, magnitude, unit vectors, projections
        • Matrices: add, multiply, transpose, inverse
        • Determinants and geometric meaning
        • Linear transformations
        • Eigenvalues and eigenvectors — core to PCA, PageRank
        • Systems of equations: Gaussian elimination

     Part 4: Calculus for ML

             CS103                 Computer Architecture & Operating                                                                          Free
                                   Systems
             Duration              6 weeks                                                                                           Intermediate

             Est. Hours            ~80 focused hours

             Prereqs               CS101
     To write fast code, you must understand the machine it runs on. This answers: why is Python slow? What
     actually happens when you type python script.py? Why does RAM size matter?

     Curriculum Breakdown
     Part 1: How Computers Work
        • Binary, hexadecimal, two's complement arithmetic
        • Boolean logic: AND, OR, NOT, XOR — these ARE the computer
        • CPU: ALU, control unit, registers, clock cycles
        • Memory hierarchy: registers > L1/L2 cache > RAM > disk — speeds matter
        • Von Neumann architecture
        • Instruction cycle: fetch, decode, execute

     Part 2: OS Fundamentals
        • What an OS does: abstraction and resource management
        • Processes vs threads — critical for ML serving and backend
        • Process lifecycle and scheduling: FCFS, SJF, Round Robin
        • Concurrency: race conditions, deadlocks — how to spot them
        • Synchronization: mutex, semaphores, condition variables
        • Memory management: paging, virtual memory, page faults
        • File systems: inodes, directories, FAT vs ext4 vs APFS

     Part 3: Linux Mastery
        • Navigation: ls, cd, pwd, find, locate, tree
        • File ops: cp, mv, rm, mkdir, touch, ln, chmod, chown
        • Process control: ps, top, htop, kill, jobs, &, nohup
        • Text processing: grep, awk, sed, cut, sort, uniq, wc, tr
        • Pipes and redirection: |, >, >>, <, 2>&1, tee
        • Shell scripting: variables, loops, if/elif, functions, $?, set -e
        • SSH, SCP, rsync, tmux, screen — essential for cloud server work
        • cron: scheduling automated tasks


              Common Mistakes — 90% of self-learners get these wrong
              Reading about Linux without actually using it — you must practice in a real terminal

              Not setting up WSL2 or a VM — there is no substitute for a real Linux environment

              Memorizing commands without understanding what they do

              Skipping the shell scripting section — every DevOps and MLOps role needs this

             CS105                                                                                                                       Free
                                   TypeScript & Type-Safe Development
             Duration              3 weeks                                                                                          Beginner

             Est. Hours            ~45 focused hours

             Prereqs               CS101
     TypeScript is no longer optional. Every serious frontend and backend role in 2025 expects it. Learning it
     now — before JavaScript habits are set — is far easier than retrofitting it later. Think of it as Python's type
     hints but for JavaScript.

     Curriculum Breakdown
     TypeScript Fundamentals
        • Why TypeScript: catches entire categories of bugs before runtime
        • Installing TypeScript: tsc, ts-node, tsconfig.json basics
        • Primitive types: string, number, boolean, null, undefined, symbol
        • Type annotations: explicit vs inferred — TypeScript is smart
        • Arrays and tuples: string[], [string, number]
        • Objects and type aliases: type User = { name: string; age: number }
        • Union types: string | number — a value can be one of several types
        • Intersection types: combining types with &
        • Literal types: type Direction = 'left' | 'right' | 'up' | 'down'

     Intermediate TypeScript
        • Interfaces vs type aliases — when to use each
        • Optional properties: name?: string
        • Readonly: readonly id: number — prevents mutation
        • Generics: function identity(x: T): T — write once, use for any type
        • Generic constraints:
        • Utility types: Partial, Required, Pick, Omit, Record
        • Enums: const enums for performance
        • Type narrowing: typeof, instanceof, in operator, discriminated unions
        • Never type: exhaustive type checking

     TypeScript in Practice
        • Strict mode: always enable it — 'strict': true in tsconfig
        • Type assertions: as Type — use sparingly
        • Type guards: custom is Type functions
        • Module system: import/export with types
        • Declaration files: .d.ts — how to type third-party libraries
        • tsconfig.json: target, lib, paths, baseUrl
        • ESLint with TypeScript: @typescript-eslint/recommended
        • Migrating JS to TS: --allowJs, gradual migration strategy


              Common Mistakes — 90% of self-learners get these wrong
              Using any everywhere — it defeats the entire purpose of TypeScript

              Ignoring TypeScript errors with @ts-ignore instead of fixing them

              Not enabling strict mode — it catches the bugs that matter most

              Learning TS without learning JS first — understand the runtime first

     Knowing how to code is not enough. Knowing how to DESIGN code is what separates junior from senior
     engineers. This subject teaches you to write code that other people can understand, safely extend, and not
     accidentally break.

     Curriculum Breakdown
     SOLID Principles
        • S: Single Responsibility — one class, one reason to change — not 'one method'
        • O: Open/Closed — open for extension, closed for modification — use abstractions
        • L: Liskov Substitution — subclasses must be substitutable without breaking behavior
        • I: Interface Segregation — don't force classes to implement methods they don't need
        • D: Dependency Inversion — depend on abstractions, not concretions — enables testing
        • Refactoring exercise: take a 300-line god class and apply SOLID step by step

     Creational Patterns
        • Singleton: only one instance — DB connection pool, config manager — use sparingly
        • Factory Method: delegate object creation to subclasses — decouples creation from use
        • Abstract Factory: create families of related objects without specifying concrete classes
        • Builder: construct complex objects step by step — separates construction from representation
        • Prototype: clone an existing object — useful when creation is expensive

     Structural Patterns
        • Adapter: make incompatible interfaces work together — legacy code integration
        • Decorator: add behavior dynamically without inheritance — Python @decorators are this
        • Facade: simplified interface to a complex subsystem — hide complexity from callers
        • Proxy: control access to an object — lazy loading, caching, access control
        • Composite: treat individual objects and compositions uniformly — tree structures

     Behavioral Patterns
        • Observer: event system — subscribe and notify — the basis of event-driven systems
        • Strategy: swap algorithms at runtime — sort by different criteria, payment methods
        • Command: encapsulate a request as an object — undo/redo, job queues, macros
        • Iterator: sequential access without exposing internals — Python's __iter__ is this
        • State: change behavior when internal state changes — traffic lights, order status
        • Template Method: define the skeleton of an algorithm, let subclasses fill details

     UML & Code Modeling
        • Class diagrams: classes, attributes, methods, relationships (association, aggregation, composition, inheritance)
        • Sequence diagrams: how objects interact over time — method call flows
        • When to draw diagrams vs when to just code — don't over-engineer
        • Reading UML in job descriptions, system design docs, and onboarding materials

              Applying patterns everywhere — patterns solve specific problems, not all problems

     Module 2: Regularization & Training Tricks

        • LSTM: cell state (long-term memory), forget gate, input gate, output gate — draw and understand every gate

     Technical interviews are a skill of their own. The best engineers fail them because they've never practiced

     Curriculum Breakdown
     Coding Interview Framework
        • UCTPV: Understand the problem fully, Clarify edge cases, Think aloud (never go silent), Plan the approach, Verify with test
           cases
        • Clarify before coding: input constraints, edge cases (empty, single element, max size), expected output format
        • Think aloud always: narrate your thought process — silence is interpreted as being stuck
        • Brute force first: state the naive O(n^2) or O(2^n) solution before optimizing — shows structured thinking
        • Optimize with questions: 'can I use extra space?', 'is the input sorted?', 'what are the constraints?'
        • Test manually: trace through 2-3 examples including edge cases before saying you're done
        • Analyze complexity: always state time and space complexity when you finish — don't wait to be asked

     The 10 Coding Patterns (Master These)
        • Sliding Window: substring/subarray with size constraint — 2 pointers that expand/shrink
        • Two Pointers: sorted array, palindrome check, 3-sum — works when order matters
        • Binary Search: sorted array, rotated array, answer-range search (minimize max, maximize min)
        • BFS/DFS: graphs, trees, grids — BFS for shortest path, DFS for existence/backtracking
        • Dynamic Programming: overlapping subproblems + optimal substructure — 5 problem families

        • Backtracking: generate all valid combinations — subsets, permutations, N-queens, word search
